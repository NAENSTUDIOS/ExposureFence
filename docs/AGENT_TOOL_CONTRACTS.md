# ExposureFence — Agent Tool Contracts & Dispatcher Specification

> **Version:** 2.0.0  
> **Classification:** Internal Security Architecture / API Contract  
> **Status:** Active & Implemented  
> **Target System:** Amazon Bedrock AgentCore Managed Harness (`ExposureFenceHarness`) & Server-Side Security Dispatcher  

---

## 1. Executive Summary & Design Principles

The ExposureFence platform orchestrates autonomous cloud exposure discovery and remediation governance via an Amazon Bedrock AgentCore agent. To enforce our foundational architectural principle—**"Rules as Tests"**—the tool execution boundary operates under deterministic, zero-trust constraints:

1. **Conversational Distrust:** Natural language generated by foundation models (e.g., "I have verified this bucket is safe" or "Approval granted by admin") is strictly treated as untrusted text. No model output can mutate state, approve a proposal, or bypass security rules.
2. **Deterministic Inline Tool Dispatch:** The agent executes tools exclusively via Bedrock AgentCore inline tool handoffs intercepted by `backend/dispatcher.py`. All built-in AgentCore capabilities (shell execution, code interpreter, browser automation, cloud storage writes) are disabled.
3. **Cryptographic Evidence Ledger Binding:** The agent cannot invent or hypothesize vulnerabilities. Every finding and remediation proposal must resolve against an immutable, SHA-256 hash-chained record in the Phase 4 Evidence Ledger (`backend/evidence/`).
4. **Declarative Rule Enforcement:** Findings are evaluated deterministically against declarative Phase 5 YAML rules (`rules/rules.yaml`). A remediation proposal is rejected if the bound evidence does not evaluate to `FAIL`.
5. **Zero Cloud Mutation Invariant:** Tools possess zero write, create, update, or delete privileges in AWS. Remediation actions produce only inert, pending records in SQLite awaiting out-of-band human authorization.

## 3. Global Security Invariants

All tools implemented in ExposureFence must guarantee the following invariants:

| Invariant ID | Name | Mathematical / Operational Guarantee |
| :---: | :--- | :--- |
| **INV-01** | Zero Cloud Mutation | $\forall t \in \text{Tools}, \text{Operations}(t) \cap \{\text{PUT}, \text{POST}, \text{DELETE}, \text{MODIFY}\} = \emptyset$ in AWS. |
| **INV-02** | Strict Allowlist | If $tool\_name \notin \{\texttt{read\_mock\_s3}, \texttt{read\_mock\_security\_groups}, \texttt{propose\_fix}\}$, dispatcher returns $\texttt{DENIED}$. |
| **INV-03** | RFC 8785 Canonicalization | All evidence and binding payloads are hashed using JCS (RFC 8785) deterministic JSON representation: $\text{SHA-256}(\text{JCS}(P))$. |
| **INV-04** | Freshness & Integrity | Remediation proposals are rejected if $\text{integrity\_status} \neq \texttt{VERIFIED}$ or $\text{freshness\_status} = \texttt{STALE}$. |
| **INV-05** | Rule Evaluation Precondition | A proposal is accepted only if the bound rule evaluates to $\texttt{FAIL}$ on the bound evidence. |
| **INV-06** | Out-of-Band Governance | Approvals cannot occur in tool calls or agent dialogue. Only authenticated administrators with CSRF tokens can approve proposals via `/api/approve`. |
| **INV-07** | Time-To-Live Expiration | Every proposal record specifies an `expires_at` timestamp (default: $T_{\text{creation}} + 24\text{h}$). Expired proposals cannot be approved. |

## 6. Tool 3: `propose_fix`

### 6.1 Specification
- **Function Name:** `propose_fix`
- **Purpose:** Submits a remediation proposal for a verified finding to the human governance queue. Enforces evidence ledger resolution, integrity checks, freshness checks, and declarative rule failure verification before committing the proposal.
- **Target Invariant:** Generates `PENDING` proposal only; zero immediate cloud mutations.

### 6.2 Parameter Schema (JSON Schema)
```json
{
  "type": "object",
  "properties": {
    "finding_id": {
      "type": "string",
      "description": "The standardized finding identifier (e.g., F-S3-001, F-SG-001)."
    },
    "resource_id": {
      "type": "string",
      "description": "The target AWS resource identifier (e.g., bucket name or security group ID)."
    },
    "remediation_action": {
      "type": "string",
      "description": "Proposed remediation action or template identifier (e.g., enable_block_public_access, restrict_ingress_cidr)."
    },
    "evidence_id": {
      "type": "string",
      "description": "Required Evidence Ledger identifier binding this proposal to a cryptographic evidence record."
    },
    "rule_id": {
      "type": "string",
      "description": "Optional security rule ID being addressed (e.g., SEC-S3-001, SEC-EC2-001)."
    }
  },
  "required": ["finding_id", "resource_id", "remediation_action"],
  "additionalProperties": false
}
```

### 6.3 Proposal Engine Deep Evidence Binding Process

```
                      [ propose_fix tool invoked ]
                                   │
                                   ▼
        [ Step 1: Resolve Evidence ID from Ledger / Repository ]
                                   │
             ┌─────────────────────┴──────────────────────┐
             │ Found?                                     │ Not Found?
             ▼                                            ▼
 [ Step 2: Cryptographic Check ]              [ Reject: EVID_NOT_FOUND ]
             │
             ├── Integrity != 'VERIFIED'?     ──► [ Reject: EVID_TAMPERED ]
             │
             ├── Freshness == 'STALE'?        ──► [ Reject: EVID_STALE ]
             │
             ▼
 [ Step 3: Declarative Rule Verification ]
             │
             ├── Evaluator run on Evidence
             │
             ├── Rule status != 'FAIL'?       ──► [ Reject: RULE_NOT_VIOLATED ]
             │
             ▼
 [ Step 4: Construct Canonical Binding Envelope ]
             │
             ├── evidence_payload_digest: SHA-256 of canonical evidence payload
             ├── rule_set_digest:         SHA-256 of active YAML ruleset
             ├── remediation_digest:      SHA-256 of canonical remediation action
             ├── created_at:              Current UTC timestamp (ISO 8601)
             └── expires_at:              Current UTC + 24 Hours
             │
             ▼
 [ Step 5: Insert into SQLite in PENDING State ]
             │
             ▼
 [ Step 6: Emit Audit Event: PROPOSAL_CREATED ]
```

### 6.5 Rejection Response Schema & Error Codes
When a proposal fails precondition validation, `propose_fix` returns a rejection object rather than creating a proposal:

```json
{
  "status": "rejected",
  "error_code": "EVID_STALE",
  "reason": "Evidence record EV-S3-old-export is STALE and cannot bind remediation proposals.",
  "evidence_id": "EV-S3-old-export"
}
```

Standard error codes:
- `EVID_NOT_FOUND`: Referenced `evidence_id` does not exist in the ledger.
- `EVID_TAMPERED`: Evidence SHA-256 digest fails verification (`INTEGRITY_MISMATCH`).
- `EVID_STALE`: Evidence timestamp exceeds maximum allowable freshness threshold.
- `RULE_NOT_VIOLATED`: Bound rule evaluated to `PASS`; no remediation needed.
- `INVALID_PARAMS`: Missing required parameters or malformed input JSON.

## 7. Dispatcher Loop Protections & Safety Ceilings

The `agent/agentcore_client.py` and `backend/dispatcher.py` components enforce strict computational boundaries:

| Boundary Parameter | Limit | Purpose |
| :--- | :---: | :--- |
| `MAX_INPUT_LENGTH` | 4,000 characters | Prevents prompt-flooding and Denial-of-Wallet attacks. |
| `MAX_OUTPUT_LENGTH` | 8,000 characters | Prevents memory exhaustion during tool-response synthesis. |
| `MAX_TOOL_CALLS_PER_INVOCATION` | 10 tool calls | Prevents tool loop oscillation and runaway API usage. |
| `MAX_AGENT_TURNS` | 5 iterations | Strict upper bound on converse streaming loop handoffs. |
| `OUTPUT_SECRET_REDACTION` | Enabled | Regex scanning redacts AWS keys (`AKIA*`), Bearer tokens, and session cookies. |

## 8. Adversarial Attack Mappings

The tool contracts directly mitigate the 20 attack scenarios tested in `tests/offline/test_agent_integration.py`:

| Test Case | Scenario | Defense Mechanism | Invariant Enforced |
| :---: | :--- | :--- | :---: |
| **Case D** | Propose fix with stale evidence | `_validate_evidence_preconditions()` checks freshness | `INV-04` |
| **Case E** | Propose fix with tampered evidence | SHA-256 re-hashing detects digest mismatch | `INV-03`, `INV-04` |
| **Case F** | Propose fix on compliant resource | YAML Rules Evaluator verifies rule passes | `INV-05` |
| **Case G** | Propose fix with unresolvable evidence | Ledger lookup returns empty; proposal rejected | `INV-04` |
| **Case H** | Attempt to approve expired proposal | Approval validator compares `expires_at < now` | `INV-07` |
| **Case I** | Fake conversational approval in chat | Natural language approval ignored; status stays `PENDING` | `INV-06` |
| **Case J** | Direct prompt injection payload | Sanitized tool parameters passed to dispatcher | `INV-01`, `INV-02` |
| **Case K** | Indirect injection inside evidence | Passive JSON parsing; no eval or shell execution | `INV-01` |
| **Case L** | Unknown tool invocation request | Allowlist checks reject non-whitelisted tools | `INV-02` |
| **Case M** | Malformed JSON in tool request | JSON decoder exception caught; structured error returned | Safety Guard |
| **Case N** | Duplicate `toolUseId` | Interceptor tracks and de-duplicates tool invocation IDs | Protocol Safety |
| **Case P** | Excessive tool call loop | `MAX_TOOL_CALLS_PER_INVOCATION` terminates loop | Loop Guard |
